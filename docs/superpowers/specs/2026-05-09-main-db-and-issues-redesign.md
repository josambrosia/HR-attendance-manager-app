# Main Database, Dashboard Default, Issues Redesign — Design Specification

**Date:** 2026-05-09 · **Status:** Draft for review · **Version:** v2.0-spec
**Builds on:** [v1.0 design](2026-05-09-josaphat-tech-attendance-design.md)

---

## 1. Overview

Three coordinated changes to v1.0 of the Josaphat Tech Solution HR Attendance Manager, all wired to the existing data model:

1. **NEW Main Database page** — monthly recap table that mirrors the user's Google Sheets format (17 columns) byte-for-byte. Built incrementally from weekly fingerprint imports + resolutions. Inline editable. Exports as `.xlsx` or copy-as-TSV for paste into Sheets.
2. **Dashboard default + range picker** — defaults to the last week that actually has imported data (was: current calendar week, which is always empty until end of week). Adds Weekly/Monthly range mode toggle.
3. **Issues page bugs + redesign** — fixes stale period text bug, replaces full-shell rebuild on nav click with partial update, redesigns issue cards (compact + auto-recommendation visible) and resolve panel (2-col grid + bigger inputs + live preview), adds 11th resolution code `tidak_hadir`.

### Goals

- Eliminate the friction caused by Dashboard always showing "no data" on weekday Mondays.
- Give HR a single editable view of the month that matches the spreadsheet she copy-pastes from at month-end.
- Make the Issues page snappy and informative — show the actual missing data, not just a name+date+badge.
- Protect manually-typed `Alasan Ijin` text from accidental overwrite during re-import.

### Non-goals

- No new database tables. Reuses existing `attendance_records` + `resolutions`.
- No multi-user / cloud sync. Same single-user, local SQLite as v1.0.
- No bulk edit, drag-to-reorder, or custom Alasan Ijin templates (deferred).

### Success criteria

- Dashboard loads on app open and immediately shows the latest imported week without manual nav.
- Main DB page renders the full April 2026 view (32 employees × 30 days = ~960 rows) in <1s after app warm-start.
- Re-importing the same week's .xls never overwrites a row that already has a resolution.
- Issues page period nav: click ▶ → list updates within ~300ms, period label always reflects displayed period.
- Main DB Export to .xlsx produces a file structurally identical to the user's `Laporan Bulanan April.xlsx` reference — same 17 columns, same row order, same separator rows.

## 4. Data Model

**No schema changes.** All needs met by existing 5 tables.

The "Main DB" view is constructed at query time as:

```sql
-- Pseudo-SQL: a LEFT JOIN that returns one row per (employee, expected workday)
SELECT
  e.staff_no, e.name, e.department,
  d.date,                              -- generated by date series
  d.day_name,                          -- "Senin", "Selasa", ...
  d.day_type,                          -- "Hari Kerja" or "Istirahat"
  ar.schedule_in, ar.schedule_out,
  ar.actual_in, ar.actual_out,
  ar.work_hours, ar.overtime_hours,
  ar.late_minutes, ar.early_leave_minutes,
  ar.absent_flag, ar.forgot_punch_flag,
  ar.issue_case,
  r.reason_code, r.location, r.reason_detail
FROM employees e
CROSS JOIN <date_series_for_month> d
LEFT JOIN attendance_records ar ON ar.employee_id=e.id AND ar.date=d.date
LEFT JOIN resolutions r ON r.record_id=ar.id
WHERE e.active=1
ORDER BY e.name, d.date
```

Rows where `ar.id IS NULL` are skeleton rows (greyed in UI, "not imported" placeholder).

The `<date_series_for_month>` is generated in Python (`calendar.monthrange` + a loop), not in SQL — SQLite's recursive CTE works but Python is simpler here.

### 5.3 `src/db/repository.py` (MODIFY)

#### Performance: partial update

`Shell._navigate` currently does `self.page.controls.clear() + self.page.add(self.build())`. For nav between sidebar items, that's fine (rare). But `_shift_week` should NOT trigger Shell rebuild — it should only update the list. Verify the existing code path: `_shift_week` already calls `self._refresh_list() + self.list_view.update()` only. The slowness is most likely from the DB query itself.

Optimize the DB query: `list_pending_issues` already filters on indexed columns (`date`, `issue_case`). Add a debounce (200ms) on rapid ◀▶ clicks to coalesce queries:

```python
def _shift_week(self, weeks: int):
    self.start += timedelta(weeks=weeks)
    self.end += timedelta(weeks=weeks)
    self.period_text.value = self._period_label()
    self.period_text.update()
    # debounce: cancel any pending refresh, schedule new one in 200ms
    self._cancel_pending_refresh()
    self._schedule_refresh(delay_ms=200)
```

Implement debounce via `threading.Timer` (a 1-shot timer canceled if another tick comes in).

### 5.6 `src/ui/pages/dashboard.py` (MODIFY)

#### Default period = last week with data

```python
def _resolve_default_period(self) -> tuple[date, date]:
    """Find the latest week with any attendance_records data.
    Falls back to current calendar week if DB is empty."""
    cursor = self.repo.conn.execute(
        "SELECT MAX(date) FROM attendance_records WHERE day_type='Hari Kerja'"
    )
    row = cursor.fetchone()
    latest_date_str = row[0] if row else None
    if latest_date_str:
        latest = datetime.fromisoformat(latest_date_str).date()
        # Snap back to Monday of that week
        start = latest - timedelta(days=latest.weekday())
    else:
        today = date.today()
        start = today - timedelta(days=today.weekday())
    return (start, start + timedelta(days=6))
```

Called in `__init__` instead of hardcoded `today.weekday()`.

#### Range mode toggle (Weekly / Monthly)

Add `self.range_mode = "weekly"` instance attr. Add toggle row above the period selector:

```python
ft.SegmentedButton(
    selected={"weekly"},
    segments=[
        ft.Segment(value="weekly", label=ft.Text("Weekly")),
        ft.Segment(value="monthly", label=ft.Text("Monthly")),
    ],
    on_change=lambda e: self._switch_range_mode(next(iter(e.control.selected))),
)
```

`_switch_range_mode` adjusts `self.start`/`self.end` to the corresponding week or month containing the current `self.start`. Period selector ◀▶ steps by week or month accordingly. All existing metric calls work unchanged — they take `start`/`end` strings.

**Inline edit semantics:**
- `actual_in`, `actual_out`: validated as `HH:MM` or empty. Updates `attendance_records.actual_in/out` via `repo.update_attendance`. Late/early/work hours are NOT recomputed automatically (they come from fingerprint export and would diverge). User can edit those columns directly too.
- `Alasan Ijin` cell: free-form text. **Stored as a synthetic resolution** with `reason_code="belum_kabar"`, the typed text in `reason_detail`, `location=NULL`. On Main DB re-render and on Excel export, the text in `reason_detail` is used directly (bypassing the standard `format_alasan` mapping when `reason_code="belum_kabar"` AND `reason_detail` is non-empty). This guarantees round-trip text preservation: HR types "Lapangan SBPM" → exact same text appears in next render and in `.xlsx` export. **Trade-off:** direct cell edits won't show up under their proper category in dashboard "Most Common Reason" or coaching analytics — for that, HR should resolve via the Issues page, which uses the structured 11-option flow.
- All other cells: editable but rarely needed; same pattern as Edit Records page in v1.0.
